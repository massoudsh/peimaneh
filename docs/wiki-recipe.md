# Vault Recipe — دستورالعمل ویکی دانش پروژه

> قالب آماده برای نگه‌داشتن یک «ویکی دانش» زنده و append-friendly کنار کد. هدف این است که وقتی این پروژه بزرگ‌تر شد و کار روی آن (با هر ابزار AI، اعم از Noqte یا هر ابزار دیگر) پیچیده‌تر شد، بشود همین دستورالعمل را در `AGENTS.md` یا `CLAUDE.md` ریشه مخزن پیست کرد تا ایجنت به‌طور خودکار طبق آن عمل کند.
>
> نسخه‌ی معادل و فعال همین سیستم هم‌اکنون در پلتفرم روی مسیر داخلی ویکی دانش پروژه اجرا می‌شود؛ این فایل نسخه‌ی قابل‌حمل آن برای استفاده مستقیم خارج از پلتفرم است.

## این چیست
یک «ویکی دانش» زنده کنار کد که به‌جای re-scan کردن کل کدبیس در هر مکالمه، خلاصه‌ی entity ها (مدل‌ها، سرویس‌ها، صفحات) و concept ها (flowها، الگوها، تصمیم‌ها) را نگه می‌دارد.
مسیر پیشنهادی: `docs/wiki/` (یا هر مسیر دیگری که پروژه ترجیح می‌دهد، به شرط ثبات).

## ساختار پوشه
```
docs/wiki/
  schema.md      # قوانین ساختار — ایجنت خودش می‌نویسد و به‌روز می‌کند
  overview.md    # یک‌نگاه کلی پروژه (≤۴۰۰ کلمه)
  index.md       # کاتالوگ همه صفحات، گروه‌بندی‌شده، با خلاصه یک‌خطی
  log.md         # تاریخچه append-only تغییرات
  entities/      # هر entity مهم یک صفحه (مدل دیتا، service، router، صفحه کلیدی UI)
  concepts/      # patternها، flowها، قراردادها، تصمیم‌های معماری
  sources/       # (اختیاری) خلاصه فایل‌های خام کدی که چندجا ارجاع داده می‌شوند
```

## شروع هر مکالمه/سشن
1. اول `overview.md` و `index.md` را بخوان (هزینه: ≤۸۰۰ توکن). هرگز کل کدبیس را re-scan نکن.
2. فقط صفحات مرتبط با تسک فعلی را drill-down کن (`entities/*.md`, `concepts/*.md`).
3. اگر `docs/wiki/` هنوز وجود ندارد، همین ساختار را با محتوای اولیه بساز.

## وقتی کد را تغییر دادی — قانون اکید
هر بار که یک فایل پروژه را تغییر می‌دهی (خارج از `docs/wiki/` خودش):
1. تشخیص بده این تغییر روی کدام entity/concept اثر می‌گذارد.
2. صفحه‌ی مربوطه را به‌روز کن (فیلد جدید/حذف‌شده، امضای تابع، route جدید، dependency جدید، edge case).
3. اگر entity/concept کاملاً جدید و به‌اندازه کافی مهم است، صفحه جدید بساز و در `index.md` لینک بده.
4. یک خط در `log.md` اضافه کن: `## [YYYY-MM-DD] update | <خلاصه تغییر>`.

تغییرات trivial (typo، فرمت، rename بدون تغییر امضا) نیاز به آپدیت ویکی ندارند.
اگر چند فایل در یک مکالمه تغییر کردند، آپدیت‌های ویکی را یک‌بار در پایان مکالمه انجام بده.

## چه وقت صفحه جدید بساز
- فقط اگر ≥۳ جای دیگر قرار است به آن لینک بدهند، یا concept مستقلی با حجم قابل‌توجه است.
- در ۹۰٪ موارد به‌جای فایل جدید، صفحه موجود را آپدیت کن.
- هرگز صفحه‌ی trivial نساز (wrapper یک‌خطی، utility ساده) — در صفحه پدر یک bullet بنویس.

## ساختار صفحه‌ی entity
```markdown
# {نام}

> یک‌خطی توضیح هدف.

## مسئولیت‌ها
- ...

## وابستگی‌ها
- [[concepts/xxx]] — چرا
- [[entities/yyy]] — چطور

## قراردادها / Edge cases
- ...

## منابع کد
- `path/to/file.ts:42` — کلاس اصلی
```

## قواعد لینک (Obsidian-style)
- `[[entities/user]]` بدون پسوند `.md`.
- نام فایل: lowercase + hyphen (`auth-flow.md` نه `Auth Flow.md`).
- wikilinkهای نمونه داخل بک‌تیک/code block لینک واقعی محسوب نمی‌شوند.

## Lint دوره‌ای (وقتی خواستید "ویکی رو بازبینی کن")
1. orphan pages (بدون inbound link) — لینک بده یا حذف کن.
2. broken link — صفحه‌ی گمشده را بساز یا لینک را حذف کن.
3. تناقض بین صفحات — flag کن، بهترین حدس را انتخاب کن و در log ثبت کن.
4. صفحات کهنه (کد مرتبط تغییر کرده ولی صفحه آپدیت نشده) — بازخوانی و sync.

## نکته نهایی
اگر این قانون رعایت نشود، ویکی stale می‌شود و مکالمات بعدی به اطلاعات غلط می‌رسند. هدف: کاهش توکن مصرفی با دانش فشرده و به‌روز — نه مستندسازی برای مستندسازی.
