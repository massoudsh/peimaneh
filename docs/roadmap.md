# نقشه‌راه محصول — پیمانه (Peimaneh)

> ایجنت هوشمند اجرای تجارت خارجی — از مکالمه خارجی تا سفارش قطعی

این سند مراحل ساخت محصول را از MVP تا نسخه‌ی بالغ مشخص می‌کند. هر فاز باید یک ارزش قابل‌لمس و قابل‌فروش تحویل بدهد، نه فقط زیرساخت.

---

## اصل راهنما در همه فازها
پیمانه **هرگز** به‌جای انسان تعهد تجاری نمی‌دهد و معامله را نمی‌بندد. هر پیشنهاد قیمت، تخفیف یا شرط پرداختی که از سقف/سیاست شرکت خارج شود، باید قبل از ارسال به تأیید انسان برسد. این قید طراحی، نه یک فیچر جانبی، محور تمام فازهاست.

## وضعیت اجرای فعلی

- **فاز ۱ پایه:** API واقعی contacts، threads، messages، policy و audit؛ رابط فارسی RTL و Docker Compose آماده است.
- **فاز ۲ پایه:** زمان‌بندی، لغو و تکمیل follow-up، فهرست فرصت‌های موعددار، جست‌وجو و ثبت رویدادها آماده است؛ worker و اعلان خودکار باقی است.
- **امنیت پایه:** bearer-token با لغو نشست، نقش‌های manager/sales، مدیریت اعضا، قفل ورود، محدودیت policy و تأیید نهایی برای manager، هویت واقعی actor در audit و hash امن رمزها آماده است.
- **زیرساخت:** migration نسخه‌دار Alembic، entrypoint مهاجرت، CI برای backend/frontend/compose و تست‌های بدون مرورگر.
- **باقی‌مانده‌های مسدودکننده انتشار:** جداسازی سازمانی، اتصال کانال رسمی، NLU/NLG، worker اعلان و آزمون runtime روی PostgreSQL/secret مدیریت‌شده.

## فاز ۰ — تعریف دامنه MVP

هدف: محدود کردن scope به یک use case قابل دمو در کوتاه‌ترین زمان.

- انتخاب **یک** دسته محصول و **یک** بازار هدف مشخص (مثلاً صادرات محصول X به عراق/امارات، یا واردات Y از ترکیه).
- انتخاب **یک** کانال ورودی اولیه — پیشنهاد: **واتساپ + ایمیل** (پرکاربردترین در تجارت خارجی ایرانی).
- انتخاب **یک** جفت زبان اولیه (فارسی ⇄ عربی یا فارسی ⇄ انگلیسی).
- تعریف اولیه‌ی «سیاست شرکت» به‌صورت ساختاریافته: کف قیمت، شرایط پرداخت مجاز، حداقل سفارش، ظرفیت تقریبی.
- خروجی فاز: سند PRD کوتاه + دیتاست نمونه از ۱۰-۲۰ مکالمه واقعی (ناشناس‌شده) برای تست پرامپت‌ها.

## فاز ۱ — دستیار مکالمه (Copilot، بدون خودکارسازی ارسال)
هدف: اثبات ارزش پایه — انسان هنوز روی «ارسال» کلیک می‌کند.

- اتصال read-only به یک کانال (مثلاً forward کردن پیام یا اتصال به ایمیل/واتساپ بیزینس API).
- خلاصه‌سازی مکالمه + تشخیص نیاز طرف مقابل (قیمت؟ نمونه؟ شرایط پرداخت؟ حمل؟).
- تشخیص سطح جدیت خریدار/تأمین‌کننده (سرنخ داغ/سرد).
- پیش‌نویس پاسخ حرفه‌ای به زبان و لحن بازار هدف (Draft، نه Auto-send).
- پیشنهاد سؤالات بعدی که تیم باید بپرسد.
- **معیار موفقیت فاز:** تیم فروش زمان نوشتن پاسخ را حداقل ۵۰٪ کاهش می‌دهد.

## فاز ۲ — پیگیری و حافظه مکالمه (Follow-up Engine)
هدف: جلوگیری از سوختن فرصت‌ها به‌خاطر فراموشی.

- ذخیره‌سازی تاریخچه مکالمه هر مخاطب (thread) با شناسه یکتا.
- تشخیص خودکار «این مکالمه نیاز به پیگیری دارد» + زمان‌بندی یادآوری.
- داشبورد ساده: لیست فرصت‌های باز، مرحله فعلی هرکدام، آخرین پیگیری، پیگیری بعدی.
- اعلان (نوتیفیکیشن داخل پنل یا ایمیل) برای follow-up های فراموش‌شده.

## فاز ۳ — موتور سیاست‌محور مذاکره (Policy-Aware Negotiation)
هدف: اجازه دادن به AI برای پیشنهاد قیمت/شرایط، اما درون چارچوب دقیق شرکت.

- ماژول «سیاست شرکت» به‌صورت config قابل ویرایش توسط مدیر بازرگانی (کف قیمت، پله‌های تخفیف مجاز، شرایط پرداخت پذیرفتنی، ظرفیت واقعی تولید/موجودی، لیست کشورها/مشتریان حساس).
- state machine مذاکره با مراحل مشخص: `inquiry → quote → sample → payment_terms → shipping → proforma → confirmation`.
- Guardrail: هر پیشنهادی که از سیاست خارج شود → به‌جای ارسال خودکار پیش‌نویس، **flag "نیاز به تأیید انسان"** می‌گیرد.
- Escalation rule: کشور/مشتری حساس → همیشه تأیید انسان، حتی اگر داخل سیاست باشد.

## فاز ۴ — مقایسه پیشنهادها (برای واردکننده‌ها)
هدف: باز کردن use case دوم بازار — واردات.

- ورودی چند پیشنهاد از تأمین‌کنندگان مختلف (متن آزاد یا فایل).
- استخراج ساختاریافته: قیمت، حداقل سفارش، زمان تحویل، شرایط پرداخت، Incoterm.
- جدول مقایسه‌ای + پرچم ریسک اولیه (مثلاً شرایط پرداخت غیرمعمول، عدم شفافیت در حمل).
- کمک به تنظیم پیام مذاکره متقابل به تأمین‌کننده.

## فاز ۵ — آماده‌سازی سفارش و اتصال به سیستم‌های داخلی
هدف: رساندن فرصت جدی تا مرحله «قابل تصمیم» برای امضا.

- تولید خودکار پیش‌نویس پیش‌فاکتور (Proforma Invoice) از داده‌های مکالمه.
- اتصال به CRM/ERP موجود شرکت (خواندن کاتالوگ، قیمت پایه، موجودی).
- Export/Sync سفارش تأییدشده به سیستم مالی یا CRM.

## فاز ۶ — گسترش کانال و زبان
هدف: مقیاس‌پذیری افقی بعد از اثبات ارزش در فاز‌های قبل.

- افزودن کانال‌های بیشتر (لینکدین، فرم‌های سایت B2B مثل Alibaba/TradeKey در صورت وجود API).
- افزودن زبان‌های بیشتر (ترکی، روسی، چینی بسته به بازار هدف مشتریان).
- شخصی‌سازی لحن به ازای بازار (مثلاً رسمیت بیشتر برای بازار آلمان، غیررسمی‌تر برای بازار عراق).

## فاز ۷ — تحلیل و بهینه‌سازی
- گزارش نرخ تبدیل فرصت → سفارش، میانگین زمان پاسخ، نرخ follow-up موفق.
- A/B روی لحن/سبک پیام برای بهبود نرخ پاسخ‌دهی طرف خارجی.
- یادگیری از تصمیمات انسانی (چه پیشنهادهایی رد شدند، چه چیزی اصلاح شد) برای بهبود سیاست‌ها.

## بررسی رقبا و اولویت‌های پیشنهادی — ۲۰۲۶-۱۰-۲۶

این ارزیابی بر معرفی‌های عمومی استوار است، نه دسترسی به محصول پولی یا مقایسه آزمایشگاهی. نبود یک قابلیت در صفحات عمومی، اثبات نبود آن در محصول نیست. دیدار و سرو CRM رقبای مجاور در مدیریت فروش هستند؛ باسکول بازار B2B و جایگزین مرحله یافتن طرف معامله است، نه لزوماً رقیب مستقیم مذاکره.

### شواهد بازار

- [دیدار، معرفی رسمی](https://www.linkedin.com/company/didarcrm): مدیریت سرنخ و مسیر فروش، پیگیری و گزارش؛ صرف داشتن dashboard تمایز کافی نیست.
- [سرو، جدول امکانات](https://www.sarveno.com/sarvcrm-price/): فرصت فروش، پیش‌فاکتور، قرارداد، پرداخت و چندارزی. چندارزی یا پیش‌فاکتور به‌تنهایی مزیت منحصربه‌فرد نیست.
- [باسکول، معرفی رسمی](https://www.linkedin.com/company/buskool): اتصال خریدار و فروشنده عمده. فرصت پیمانه ادامه کار پس از کشف مخاطب است؛ دسترسی API یا همکاری باسکول تأیید نشده است.

### ممیزی فایل‌ها، جریان‌ها و UX

روش: بررسی فایل‌های tracked و hash محتوا، مسیرهای API و فرم‌ها؛ ارزیابی heuristic بر اساس پیشگیری از خطا، کمینه‌سازی ورودی، وضعیت روشن و حفظ داده. این بررسی visual benchmark یا گواهی WCAG نیست؛ مرورگر اجرا نشده است.

**اصلاح‌شده در ممیزی ۲۰۲۶-۱۱-۱۶:**
- ثبت‌نام عمومی حذف شد: فقط `bootstrap` صریح و manager-only برای ساخت نخستین حساب و مدیریت اعضا باقی مانده است.
- logout، لغو همهٔ نشست‌ها، غیرفعال‌سازی حساب، قفل ۱۵دقیقه‌ای پس از پنج تلاش ناموفق و هویت واقعی actor در audit اضافه شد.
- انتقال مرحله از endpoint سرور (`/threads/{id}/transitions`) می‌آید و تأیید نهایی فقط برای مدیر مجاز است.
- رابط فارسی و RTL شد؛ نقش sales لینک سیاست/تیم را نمی‌بیند، audit pagination دارد، جست‌وجوی مخاطب/فرصت اضافه شد و خطاها به‌صورت پیام روشن نمایش داده می‌شوند.
- migration نسخه‌دار Alembic و drift check در CI اضافه شد؛ startup دیگر جدول نمی‌سازد.
- compose از env استفاده می‌کند، سلامت دیتابیس/بک‌اند را gate می‌کند، پورت‌ها را روی loopback می‌بندد و image بک‌اند با کاربر غیر root اجرا می‌شود.
- آسیب‌پذیری‌های ورودی: قیمت/تخفیف غیرمتناهی، نام خالی و پیام blank رد می‌شوند؛ مقایسهٔ سیاست بدون حساسیت به حروف است.
- ذخیره نسخه policy دیگر `capacity_notes` و `sensitive_customers` ناموجود در فرم را پاک نمی‌کند.
- pagination در hash همان صفحه نگهداری می‌شود؛ offset فرصت‌ها به پیگیری‌ها نشت نمی‌کند و مقادیر منفی/اعشاری/نامحدود پذیرفته نمی‌شوند.
- مسیر خالی به overview می‌رود، نه «page not found»؛ company و country واقعاً اختیاری‌اند؛ برای فرصت confirmed فرم زمان‌بندی نمایش داده نمی‌شود.

**حفظ‌شده با دلیل:** فقط دو `__init__.py` خالی hash یکسان دارند؛ هر دو marker بسته Python هستند. README ریشه و backend مخاطب متفاوت دارند. docs معماری/roadmap/PRD و ویکی نقش متفاوت دارند؛ حذف عمده بدون اثبات بلااستفاده بودن انجام نشد. پوشه db خالی در Git وجود ندارد؛ PostgreSQL سرویس compose و volume است.

**باقی‌مانده‌ها، به‌ترتیب اهمیت:**
1. جداسازی سازمانی (multi-tenant) وجود ندارد؛ همهٔ کاربران یک فضای کاری مشترک دارند و onboarding باید دعوت‌محور شود. هنوز آماده انتشار عمومی نیست.
2. اتصال رسمی کانال‌ها و NLU/NLG واقعی پیاده نشده است؛ ارسال خودکار عمداً وجود ندارد.
3. worker اعلان پیگیری، inbox و idempotency اعلان باقی مانده است.
4. audit فقط برای threadها و ساخت policy است؛ گزارش‌های سازمانی و export وجود ندارد.
5. محیط visual/accessibility با مرورگر بررسی نشده است (اجرای مرورگر در این محیط ممنوع است)؛ بازبینی RTL و کیبورد باید توسط تیم انجام شود.
6. Docker imageها در این محیط build نشده‌اند و runtime PostgreSQL آزمون نشده است؛ CI فقط config را validate می‌کند. مقادیر `.env.example` توسعه‌ای هستند.

آزمون‌های بدون مرورگر: `node --test frontend/test-app.cjs` (۱۴ تست) و ۳۲ تست backend. Docker build در این محیط اجرا نشد.


## اولویت‌بندی پیشنهادی برای شروع
اگر منابع محدود است، ترتیب MVP → PMF: **فاز ۰ → ۱ → ۲ → ۳**. فاز ۴ (مقایسه واردات) و فاز ۵ (پیش‌فاکتور) را می‌توان بسته به اینکه مشتری اول صادرکننده است یا واردکننده، جابه‌جا کرد.
